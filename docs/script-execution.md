# Proposal: opt-in userscript callbacks and structured results

An agent developing a userscript can currently install or update it, reload a granted tab, and inspect `GM_log` output. Testing a function with several inputs requires editing the script or adding an application-specific trigger. Log strings also require an application-specific convention to associate an asynchronous result with the request that produced it.

This proposal adds one explicitly registered callback per script and frame, plus a bounded channel for structured results. An agent could call a script's validation or calculation function with JSON input and receive its return value or error without rerunning the script's top-level initialization. A script could also deliberately report a result from an event it observes.

## Scope decision

The current [development contract](contract.md#non-goals) excludes externally driving userscripts and treats `GM_log` as the feedback boundary. Callable handlers would intentionally extend that scope. This proposal asks whether that extension is desirable before requesting a release; it does not assume that callback registration alone resolves the product or permission decision.

Invocation requires a connected MCP session, an explicitly granted tab, an enabled installed script and a handler registered in that document. Scripts opt in using `@grant GM_registerMcpHandler` and an explicit registration call. Results contain only what the script returns or reports. No generic evaluation, DOM query, navigation, console capture or network capture tool is added. Registration is an application-level opt-in, not a new security sandbox: an agent already allowed to edit scripts can add a handler, and a handler can perform the same actions as its userscript.

File saving, download directories, local filesystem access and application-specific integrations are deferred to a separate proposal. Existing `GM_download` behavior is unchanged.

## Userscript API

```js
// ==UserScript==
// @name         MCP calculation example
// @namespace    mcp-example
// @version      1.0.0
// @match        https://example.com/*
// @grant        GM_registerMcpHandler
// @grant        GM_reportResult
// ==/UserScript==

GM_registerMcpHandler(async (params, { callId }) => {
  if (!params || typeof params.a !== 'number' || typeof params.b !== 'number') {
    throw new Error('Expected numeric a and b');
  }
  return { sum: params.a + params.b, callId };
});

// Optional unsolicited report; does not register a callable handler.
GM_reportResult({ event: 'ready' });
```

`GM_registerMcpHandler(handler)` resolves after registration is acknowledged. A later registration replaces the callback for that script in that frame. The callback receives JSON input and `{ callId }`, and may return synchronously or asynchronously. `undefined` becomes `null`; other values must be JSON serializable. Thrown errors, rejected promises and invalid return values become failed execution records.

`GM_reportResult(value, { callId?, error? }?)` returns `{ accepted, callId }`. Without a call ID it creates an unsolicited record. With a call ID it completes only a matching call from the same script, frame and document channel. The first terminal reply wins; duplicate replies return `accepted: false`. Callbacks normally return their value directly. `GM.registerMcpHandler` and `GM.reportResult` provide the corresponding namespaced APIs.

## MCP tools

| Tool | Input | Output |
| --- | --- | --- |
| `script_handlers` | `tabId` | `handlers: [{ scriptId, frameId }]` |
| `script_call` | `tabId`, `scriptId`, optional `frameId`, `params`, `callId`, `wait`, `timeoutMs` | `result: Execution` |
| `script_results` | `tabId`, optional `scriptId`, `callId`, `afterSeq`, `limit` | `entries: Execution[]`, `nextSeq`, `dropped` |

All three tools require tab authorization. `script_call` defaults to frame 0, `params: null`, `wait: true` and a 10-second execution timeout; the permitted timeout is 1–25,000 ms. The server's default 30-second transport timeout leaves time to return an execution timeout record. Deployments overriding that transport timeout should keep it above the requested execution timeout.

An execution record contains `callId`, `scriptId`, `frameId`, an opaque `documentId`, `seq`, `startedAt`, `status`, and optional `finishedAt`, `value` or `error`. Status is `pending`, `completed`, `failed`, `timed_out` or `cancelled`. Timestamps are milliseconds since the epoch. Call IDs are nonempty strings of at most 128 characters, generated by the extension when omitted.

For example, after discovering the installed script and granting and reloading its tab:

```json
{"tabId": 7, "scriptId": 1, "params": {"a": 2, "b": 3}, "callId": "sum-1"}
```

Pass this to `script_call`; a successful execution returns `result.status: "completed"` and `result.value.sum: 5`. For long-running work, use `wait: false` and poll `script_results` with the returned call ID. Reads default to 50 entries and allow 1–100; `afterSeq` is an exclusive cursor and `nextSeq` can be used for the next read. Reads do not consume records, and `dropped` counts evictions cumulatively for the tab's session.

## Errors, limits and lifecycle

Protocol errors cover invalid arguments, missing handlers and denied access. Script errors are returned in a valid execution record; a successful MCP request does not imply a successful script. Read-only mode exposes handler discovery and result reads, but excludes `script_call`, which is marked potentially destructive and open-world.

A timeout ends the wait, not the script or its side effects. A late reply can update a retained `timed_out` record to `completed` or `failed`. Reusing a retained call ID with the same script, frame and serialized parameters returns the existing record without invoking the callback again. Different arguments with that ID fail. Eviction, disconnect or restart removes this deduplication guarantee; there is no durable exactly-once execution. Clients should not automatically retry side effects with a fresh ID.

The extension limits serialized input and output to 256 Ki characters each, errors to 8,192 characters, and pending calls to 32 per tab. Terminal records expire after five minutes; count and byte pressure may evict them earlier. Retention is capped at 100 records and approximately 2 MiB per tab, with pending calls protected from eviction and bounded separately by the per-call and concurrency limits.

Navigation or reload cancels unfinished calls for the replaced document. Closing a tab, revoking its grant or disconnecting clears its channels and retained results. These operations do not undo effects already performed by a script. Back/forward cache restoration renews the channel and restores registered handlers without rerunning script initialization, provided the original authorization session still exists. Old calls are not replayed and old channel replies remain invalid. Main frames and child frames can restore in either order. A revoked or replaced session requires explicit authorization and a reload.

## Implementation and compatibility

The MCP repository owns the three tool schemas, typed client interfaces, capability negotiation and transport tests. The companion extension change owns the GM APIs, authorization checks, per-document dispatch, result retention and page lifecycle. Tools are exposed only when both server and extension support them; existing extensions retain their current tool list. The existing JavaScript client transport can advertise the new names, while a protocol/client package release makes them available to typed consumers.

No package version or minimum extension release is assigned by this draft. Coordinate the MCP package release and extension rollout if the proposal is accepted. The extension can be tested against a local build of this repository before publishing.

## Questions for maintainers

1. Is explicit callback invocation an acceptable extension of the current development-only scope, or should the initial feature be limited to unsolicited structured reports?
2. Are two new GM APIs appropriate, and should the proposed names or registration model change?
3. Is the existing per-tab grant sufficient, or should invocation require an additional user-facing permission?
4. Are the timeout, retention, deduplication and back/forward cache semantics suitable for an initial version?

The companion tests cover correlation, failures, expiry, authorization, navigation and restoration. Before requesting merge, browser verification should cover Chrome and Firefox, both script realms, child frames, and actual persisted `pageshow` events.
